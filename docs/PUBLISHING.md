# Как опубликовать это: пошагово

Инструкция для того, кто с GitHub раньше не работал. Делайте по порядку,
ничего не пропуская — особенно шаг 0.

---

## Шаг 0. Проверка на утечки — обязательно

В репозиторий не должны попасть ваши токены, Apple ID и пути с вашим именем
пользователя. Токен даёт полный доступ к медиатеке; Apple ID — это ваш
идентификатор в системах Apple.

Откройте Терминал и выполните из папки репозитория:

```bash
cd "путь/к/apple-music-library-restore"

# 1. Файлы, которых быть не должно: токены, рабочие отчёты, ваша выгрузка
find . -maxdepth 2 -not -path "./.git/*" \
  \( -name tokens.json -o -name "*.csv" -o -name work -o -name "*_journal.json" \)

# 2. Заполненные токены в любом файле — ловит оба формата Apple
grep -rIn -E '"(developer_token|music_user_token)"[[:space:]]*:[[:space:]]*"[^"<]{40,}"' . \
  --exclude-dir=.git

# 3. JWT-токены где угодно, даже вне tokens.json (вдруг попали в лог)
grep -rIn -E 'eyJ[A-Za-z0-9_-]{20,}\.[A-Za-z0-9_-]{20,}' . --exclude-dir=.git

# 4. Личные пути с вашим именем пользователя
grep -rIn -E "/Users/[a-z]" . --exclude-dir=.git --exclude=PUBLISHING.md
```

**Все четыре команды должны не вывести ничего.** Пустой вывод — это то, что
нужно; `grep` при этом вернёт код 1, и это нормально, а не ошибка.

> **Почему команды именно такие — тут я сам наступил на грабли.**
>
> Первая ищет через `find`, а не `ls`: в zsh — оболочке macOS по умолчанию —
> `ls *.csv` при отсутствии файлов выдаёт `no matches found` и сбивает с толку.
>
> В первой версии этой инструкции я искал токены по подстроке `eyJhbGciOi` —
> это начало типичного JWT, где первым полем идёт `alg`. Проверил на настоящих
> токенах: **не находит ни одного**. У Apple developer token начинается с
> `eyJ0eXAi` (первым идёт `typ`), а music-user-token вообще не JWT — он в
> формате `0.AgOCMbyz…`. Проверка выглядела работающей и не защищала ни от чего.
>
> Поэтому теперь их две. Одна ищет **заполненные поля токенов** — ей всё равно,
> какого формата значение внутри. Вторая ищет JWT по устройству, а не по
> началу: две длинные части через точку. Обе проверены на настоящих токенах —
> находят; на `tokens.example.json` с заглушками — молчат.
>
> Мораль, применимая к любой самопроверке: **проверку на утечки надо
> протестировать на настоящей утечке.** Иначе вы просто смотрите на пустой
> вывод и успокаиваетесь.

Если что-то нашлось — удалите файл или вычистите строку. Помните: удалить файл
из репозитория после первой публикации **недостаточно**, он останется в
истории. Проще не допустить.

Заодно проверьте `LICENSE` — в строке `Copyright (c)` должно стоять имя
правообладателя, а не заглушка. По конвенции там указывают настоящее имя
владельца прав; ник тоже работает, но доказывать авторство с ним сложнее. Год
— год первой публикации, обновлять его ежегодно не нужно.

## Шаг 1. Регистрация на GitHub

1. Откройте [github.com/signup](https://github.com/signup)
2. Укажите почту, придумайте пароль и имя пользователя

   Имя пользователя попадёт в адрес репозитория:
   `github.com/ваш-ник/apple-music-library-restore`. Выбирайте то, что не
   стыдно показать.
3. Подтвердите почту по письму
4. Тарифа хватит бесплатного — публичные репозитории на нём без ограничений

**Сразу включите двухфакторную аутентификацию:** Settings → Password and
authentication → Two-factor authentication.

Это не пожелание, а требование GitHub: с марта 2023 года двухфакторная
аутентификация обязательна для всех, кто публикует код, а с 19 января 2024
года доступ к аккаунту без неё ограничивается — вас будет перенаправлять на
страницу настройки, пока не включите. Проще сделать сразу, чем упереться в это
на середине публикации.

## Шаг 2. Создание репозитория

Нажмите **+** справа вверху → **New repository**. На форме будет больше полей,
чем нужно, — большинство пропускаем.

| Поле | Что делать |
|---|---|
| **Owner** | ваш ник, менять не надо |
| **Repository name** | `apple-music-library-restore` |
| **Description** | текст ниже, скопируйте целиком |
| **Public / Private** | **Public** |
| Choose a template | пропустить |
| Add a README file | **не ставить** — свой уже есть |
| Add .gitignore | **не ставить** — свой уже есть |
| Choose a license | **не ставить** — своя уже есть |
| Marketplace Apps | пропустить |
| Copilot prompt | пропустить, код у нас готов |

Затем **Create repository**.

### Про имя — вы остановились именно здесь

Возьмите **`apple-music-library-restore`**.

Имя репозитория — половина поисковой выдачи: GitHub и Google ищут по нему, по
описанию и по тексту README. Название должно состоять из слов, которые человек
набирает в поиске, когда у него случилась ваша беда: `apple music`, `library`,
`restore`. Всё это в нём есть.

Не называйте репозиторий `am-tools`, `music-migrator` или `my-scripts` — такое
имя не найдёт никто, включая вас через год.

Технические ограничения GitHub: до 100 символов, только латинские буквы,
цифры, точка, дефис и подчёркивание. Пробелы автоматически заменяются на
дефисы. Наше имя проходит с запасом.

### Описание — скопируйте дословно

```
Restore your Apple Music library after changing your Apple ID country, using Apple's own data export
```

Это поле показывается в результатах поиска прямо под именем. Оно должно
отвечать на два вопроса сразу: что это и кому нужно. Здесь есть и проблема
(«changing your Apple ID country»), и решение («restore your library»), и
средство («Apple's own data export»).

Описание на английском, потому что проблема международная. Русскоязычные
читатели придут из статьи на Хабре, и для них есть `README.ru.md`.

## Шаг 3. Загрузка файлов

Два пути. Первый проще, второй правильнее.

### Путь А — через браузер (проще)

1. На странице пустого репозитория нажмите **uploading an existing file**
2. Перетащите в окно **всё содержимое** папки `apple-music-library-restore`:
   - `01_check.py`, `02_resolve.py`, `03_add_tracks.py`, `04_add_playlists.py`
   - `common.py`, `test_logic.py`
   - `README.md`, `README.ru.md`, `LICENSE`, `SECURITY.md`
   - `.gitignore`, `tokens.example.json`
   - папку `docs` целиком
3. В поле Commit changes напишите `Initial commit`
4. **Commit changes**

> Файл `.gitignore` начинается с точки, и Finder его по умолчанию не
> показывает. Нажмите `Cmd + Shift + .`, чтобы скрытые файлы стали видны.

### Путь Б — через Терминал (правильнее)

```bash
cd "путь/к/apple-music-library-restore"

git init
git add .
git status          # ← ОБЯЗАТЕЛЬНО посмотрите список глазами
```

В выводе `git status` **не должно быть** `tokens.json`, папки `work/` и
никаких `.csv`. Если они там есть — значит `.gitignore` не подхватился,
остановитесь и разберитесь.

```bash
git commit -m "Initial commit"
git branch -M main
git remote add origin https://github.com/ВАШ-НИК/apple-music-library-restore.git
git push -u origin main
```

При запросе пароля обычный пароль от аккаунта не подойдёт — GitHub его больше
не принимает. Нужен **Personal Access Token**: Settings → Developer settings →
Personal access tokens → Tokens (classic) → Generate new token, права `repo`.
Скопируйте его и вставьте вместо пароля.

Проще обойтись без этого через официальный клиент GitHub. Он сам откроет
браузер для входа, и возиться с токенами не придётся:

```bash
brew install gh
gh auth login          # выберите GitHub.com → HTTPS → Login with a web browser
gh repo create apple-music-library-restore --public --source=. --push
```

Последняя команда создаёт репозиторий и заливает файлы за один раз — то есть
заменяет собой и шаг 2, и весь путь Б. Если пошли этим путём, описание и топики
всё равно проставьте вручную по шагу 4.

> Команды `git` из пути Б я проверял, `gh` — нет: его не было в системе.
> Если `gh auth login` поведёт себя иначе, чем описано, ориентируйтесь на
> подсказки в самом клиенте, они там понятные.

## Шаг 4. Оформление репозитория

Это напрямую влияет на находимость.

1. На странице репозитория нажмите ⚙️ рядом с **About** справа
2. **Description:** тот же текст, что при создании
3. **Topics** — добавьте ровно эти семь, по одному:

   ```
   apple-music   apple-music-api   music-library
   library-migration   storefront   data-export   python
   ```

   Топики — метки, по которым ищут внутри GitHub. Рабочий диапазон —
   **пять-восемь**: этого хватает, чтобы покрыть язык, предметную область и тип
   проекта. Больше десятка выглядит как спам и размывает смысл, поэтому я
   сократил список — в первой версии этой инструкции их было десять, и это было
   лишним.

   Важно, чтобы топики **не противоречили** имени, описанию и README: GitHub
   оценивает их согласованность.
4. Снимите галочки с **Packages** и **Environments**, они пустые
5. Сохраните

Проверьте, что `README.md` отобразился на главной странице и что в нём работает
ссылка на русскую версию.

### Картинка для соцсетей

Когда кто-то кинет ссылку на ваш репозиторий в Telegram, Twitter или Slack,
развернётся превью. По умолчанию там серая картинка-заглушка с именем
репозитория — выглядит блёкло и снижает переходы.

**Settings → General → Social preview → Edit → Upload an image.**

Требования: PNG, JPG или GIF, **до 1 МБ**, рекомендуемый размер
**1280 × 640 пикселей** (минимум 640 × 320). Картинку обрезают в пропорции 2:1,
поэтому всё важное держите по центру и не подводите текст ближе 50 пикселей к
краю.

Сойдёт что угодно осмысленное: скриншот «до и после» из приложения «Музыка»
или просто название проекта крупным шрифтом на однотонном фоне. Проверьте,
чтобы на скриншоте не было вашей почты и Apple ID.

## Шаг 5. Защита от случайной утечки токенов

Отдельный шаг, потому что проект работает с ключами доступа к чужим
медиатекам, и цена ошибки высокая.

GitHub бесплатно даёт публичным репозиториям **secret scanning** и **push
protection**: он проверяет то, что вы отправляете, и **блокирует отправку**,
если находит похожее на ключ доступа. Для публичных репозиториев это включено
по умолчанию — но проверьте:

**Settings → Advanced Security** (или *Code security and analysis*) →
**Secret scanning** и **Push protection** должны быть включены.

> ⚠️ **Не полагайтесь на эту защиту.** Она знает несколько десятков форматов
> ключей известных сервисов — AWS, Stripe, GitHub и подобных. Токены Apple
> Music в этот список, скорее всего, не входят, так что ваш `tokens.json`
> система пропустит молча. Проверка из шага 0 остаётся единственной настоящей
> защитой, а push protection — приятной подстраховкой на случай, если в
> репозиторий попадёт что-то другое.

Заодно включите **Dependabot alerts** там же — предупреждает об уязвимостях в
зависимостях. У нас зависимостей нет вообще, так что пользы никакой, но
привычка полезная.

## Шаг 6. Порядок публикации — он важнее, чем кажется

Соблазн — залить репозиторий и сразу постить ссылку везде. Так делать не надо,
и вот почему.

Пустой репозиторий без единой звезды, без описания в About и с одним коммитом
выглядит заброшенным. Человек, пришедший по ссылке в первый день, оценит
проект за пять секунд и закроет — а второй раз он не придёт.

Разумный порядок:

1. **Сначала доводим репозиторий до готового вида** — описание, топики,
   картинка превью, README на месте и читается. Это шаги 2–5.
2. **Потом статья на Хабре** со ссылкой на репозиторий. Читатели статьи
   приходят уже подготовленными: они прочитали, зачем это, и переходят по
   ссылке за инструментом, а не разбираться, что тут вообще.
3. **Потом Reddit и остальное** — через день-два, когда по ссылке из статьи
   уже кто-то зашёл.

Разница в том, что человек из поиска видит голый репозиторий и решает сам,
стоит ли разбираться. Человек из статьи уже знает ответ.

Ещё одна мелочь, которая сильно влияет на первое впечатление: **добавьте
ссылку на статью в README** сразу после публикации. Тогда пришедшие из поиска
попадут в подробный рассказ, а не в сухую инструкцию.

## Шаг 7. Статья на Хабре

Именно она даст основной трафик: аудитория русскоязычная, и по таким запросам
Хабр выходит в топ Google за считаные дни.

1. Зарегистрируйтесь на [habr.com](https://habr.com)

   > Новые аккаунты на Хабре публикуются через «Песочницу»: первая статья
   > проходит премодерацию, и если она полезная — аккаунт получает полные
   > права. Техническая статья с реальными измерениями проходит нормально.

2. Возьмите за основу `docs/article-ru.md`
3. **Обязательно перепишите вступление под себя.** Личная история — то, ради
   чего такие статьи читают. Замените все места вида `[...]` и удалите мои
   комментарии в блоках-цитатах.
4. Вставьте ссылку на репозиторий в конце
5. Хабы: **Apple**, **Python**, **Разработка**
6. Формат: **Туториал**
7. Заголовок — под то, что люди реально гуглят. Варианты:
   - «Как я вернул медиатеку Apple Music после смены страны аккаунта»
   - «Сменил регион Apple ID и потерял всю медиатеку. Как я её восстановил»

Скриншоты сильно помогают: до/после в приложении Музыка, кусок
`manual_review.csv`, вывод скрипта. Только проверьте, чтобы на них не попали
ваш Apple ID и почта.

## Шаг 8. Англоязычная аудитория

Проблема международная — смена страны ломает медиатеку у всех.

- **r/AppleMusic** — пост с кратким описанием и ссылкой на репозиторий.
  Reddit не любит голые ссылки: напишите пару абзацев по существу, расскажите
  цифры, ссылку дайте в конце.
- **r/apple** — туда же, но там строже с саморекламой, читайте правила сабреддита.
- **[Apple Support Communities](https://discussions.apple.com)** — найдите
  живые треды про потерю медиатеки при смене страны и ответьте по делу со
  ссылкой. Такие обсуждения хорошо ранжируются в Google годами.

## Если что-то пошло не так

**«Repository name already exists»** — у вас уже есть репозиторий с таким
именем. Либо загружайте файлы в него, либо добавьте суффикс: `-py`, `-tool`.

**Запушил `tokens.json` по ошибке.** Удалить файл новым коммитом
**недостаточно** — он останется в истории и будет доступен по прямой ссылке.
Порядок действий: сразу выйдите из Apple Music на `music.apple.com` (это
обнулит токен), затем удалите репозиторий целиком в Settings → General →
Delete this repository и создайте заново из чистой папки. Для разового проекта
это быстрее и надёжнее, чем чистить историю git.

**`git push` спрашивает пароль и не принимает его.** GitHub перестал принимать
пароли аккаунта. Нужен Personal Access Token или `gh auth login` — оба способа
описаны в шаге 3.

**README отображается, но таблицы «поехали».** Проверьте, что перед таблицей и
после неё есть пустая строка — Markdown требует этого.
