# Замеры и поведение API

**English version: [FINDINGS.md](FINDINGS.md)**

Всё здесь измерено на реальном переезде **6 августа 2026**, Apple Music API v1,
витрина `RU` → `US`. Исходная медиатека: 10 532 трека, копившиеся с 2012 по
2026 год. Размер выборки указан для каждой цифры.

Apple меняет этот API без предупреждения. Если вы читаете это заметно позже —
перемерьте сами через `01_check.py`, прежде чем верить написанному ниже.

---

## 1. Каталожные ID привязаны к витрине

Тот самый факт, из-за которого наивный перенос не работает. У одной и той же
песни в каждой стране свой числовой идентификатор, потому что в разных
витринах могут лежать разные издания одной записи.

Замерено на двух независимых случайных выборках из одной медиатеки:

| Выборка | Исходных ID, работающих в целевой витрине |
|---|---:|
| n = 100 | 63% |
| n = 150 | 66% |

То есть **примерно каждый третий ID** в чужой витрине не значит ничего.

## 2. Три способа перевести ID, и они не равноценны

### `filter[equivalents]`

```
GET /v1/catalog/{target}/songs?filter[equivalents]={source_id}
```

Собственный конвертер Apple между витринами. Целевая витрина — в пути запроса,
исходный ID — в фильтре.

- **Охват:** 39 из 51 неразрешённого трека (76%)
- **Точность:** 87% в пределах 5 секунд от исходной длительности
- **Принимает один ID за запрос** — пачками нельзя, и именно это определяет
  общее время работы

### ISRC

```
GET /v1/catalog/{source}/songs?ids={source_id}      → attributes.isrc
GET /v1/catalog/{target}/songs?filter[isrc]={isrc}
```

- **Охват:** 12 из 51 (24%)
- **Точность:** **100%** — все совпадения в пределах 2 секунд от исходной
- **Пачками до 100 ID**, поэтому стоит почти ничего

### Очная ставка

На одних и тех же 51 треке, где оба метода что-то нашли:

| | |
|---|---:|
| Совпали на одном и том же ID | 5 |
| **Разошлись** | **7** |
| Нашёл только ISRC | 0 |
| Нашёл только конвертер | 27 |

Во всех семи расхождениях прав был ISRC. Сверх конвертера он не находит
ничего, но и не ошибается.

**Отсюда порядок в каскаде: ISRC → прямой ID → конвертер.** Не «сначала
дешёвые»: прямая проверка ошибается в 4% случаев, и поставленная первой она
застолбит около 190 неверных версий — найденное на раннем шаге дальше уже не
перепроверяется.

## 3. Конвертер подменяет версии треков

Тот самый режим отказа, ради которого стоит читать этот файл. Реальные
примеры:

```
Dario G — Sunchyme (Radio Edit)       → Sunchyme                        расх. 144 с
Arty — The Wall (Radio Edit)          → The Wall (Original Extended Mix) расх. 234 с
Gouryella — Gouryella                 → Gouryella                        расх. 422 с
Pet Shop Boys — Rent (Seven-Inch Mix) → Rent                             расх.  92 с
```

Закономерность устойчивая: радиоверсию подменяет оригинал или расширенный
микс. Если у вас танцевальная музыка, транс или электроника — это заденет
заметную долю медиатеки.

Прямые совпадения по ID тоже не застрахованы: 4% оказались не той версией,
например `Sunlite & Aki — Boogie Time` → `Boogie Time (Radio House Mix)`,
расхождение 126 с.

**Длительность — единственный дешёвый различитель.** Использованные пороги:

| Расхождение | Вердикт | Действие |
|---|---|---|
| ≤ 2 с | exact | добавляем |
| ≤ 5 с | close | добавляем |
| ≤ 30 с | suspect | глазами |
| > 30 с | different | глазами |

Отдельно: латиница в имени исполнителя сама по себе не проблема —
`Каста → Kasta` с разницей в 8 секунд обычно та же запись из другого релиза.
Судить надо по длительности, а не по написанию.

## 4. Запись в медиатеку работает только на другом хосте

| Хост | GET | POST | DELETE |
|---|---|---|---|
| `api.music.apple.com` | ✅ | ✅ | **401** |
| `amp-api.music.apple.com` | ✅ | ✅ | ✅ 204 |

Веб-плеер ходит на `amp-api`. `DELETE` на задокументированный хост возвращает
401 с пустым телом независимо от заголовков — пробовали с `Origin`, `Referer`
и браузерным `User-Agent` и без них. Тот же токен, та же секунда, на `amp-api`
работает.

Без этого нет отката, а значит большой перенос превращается в операцию в один
конец.

## 5. HTTP 202 не значит, что трек добавлен

`POST /v1/me/library?ids[songs]=...` возвращает `202 Accepted` и обрабатывает
запрос асинхронно. Часть треков не появляется никогда.

- отправлено 6 665 треков → подтверждено в медиатеке 6 428
- **237 (3,5%) приняты и молча потеряны**
- повтор ничего не меняет; отправка по одному ничего не меняет
- эти треки есть в целевом каталоге и нормально играют — проверено через
  `GET /v1/catalog/{sf}/songs/{id}`, `playParams` на месте

По составу это сезонные сборники и концертные альбомы (рождественские записи
Синатры, живые сеты). Читается как лицензия на конкретный релиз, разрешающая
стриминг, но не добавление в медиатеку. **Всегда сверяйте результат после
заливки — ответу 202 верить нельзя.**

## 6. Мёртвые записи в медиатеке

Личные загрузки (iTunes Match), у которых кончилась подписка, оставляют после
себя записи с метаданными, но **без `playParams`**:

```json
{ "name": "Артист - Название", "durationInMillis": 176195,
  "albumName": "", "trackNumber": 0 }
```

Ни обложки, ни имени исполнителя, играть нечего. В приложении «Музыка» они
серые. В новом аккаунте такими оказались 218 из 243 ранее существовавших
записей.

Два следствия:

1. **Не считайте их при дедупликации** — иначе пропустите добавление живого
   трека, потому что рядом лежит надгробие с тем же названием.
2. **Личные загрузки невосстановимы** после того, как облачные копии удалены.
   Помогает только локальная резервная копия.

## 7. Альбомы и исполнители восстанавливаются сами

Добавление треков само подтянуло **3 490 альбомов и 2 284 исполнителя** —
больше, чем 2 625 и 1 688 в исходной медиатеке, потому что треки приносят с
собой весь альбом целиком.

Отдельный проход по импорту альбомов был запланирован и оказался не нужен.
`02_resolve.py` по-прежнему разрешает ID альбомов, но импортировать их явно
обычно избыточно и рискованно: медиатека раздувается треками, которых у вас
никогда не было.

## 8. Плейлисты

- Порядок треков сохраняется в `Playlist Item Identifiers` в выгрузке
- Дубли внутри плейлиста — обычное дело: в одном каждый трек был перечислен
  дважды (104 позиции, 59 уникальных)
- Плейлисты, которые уже существуют и доступны для правки, надо **наполнять,
  а не пересоздавать**, иначе получите дубликаты
- `Favorite Songs` принадлежит системе (`canEdit: false`), писать в него
  нельзя — он наполняется из оценок
- Кураторские плейлисты Apple добавляются обратно по
  `Public Playlist Identifier`; из 47 ещё существовал 41
- **Осторожно с одноимёнными плейлистами.** Журнал по одному имени молча
  пропускает второй такой же. Ключ должен быть «имя + индекс».

Выгрузка содержит состав не всех плейлистов: 150 из 190 пользовательских
приехали с одними названиями.

### Плейлисты, которые остаются на Маке и не доходят до телефона

Замечено на втором переезде: исходного аккаунта уже нет, медиатеку
восстанавливали из приложения «Музыка» на Маке. Четыре плейлиста были на
Маке, но не в облачной медиатеке, поэтому на айфон так и не попали.

- **Треки-болванки.** Треки, которые лежали в плейлисте, но не в медиатеке
  (`Playlist Only` в XML-выгрузке), смену аккаунта не пережили. «Музыка»
  заменила каждый пустым `URL track` («Поток интернет-аудио», без адреса,
  `cloud status = unknown`). Такие нашлись в двух плейлистах: 18 из 98 и 33
  из 86. Обоих не было в облаке, а все редактируемые плейлисты без болванок,
  созданные в ту же секунду, залились нормально. Это совпадение на 2 из 2, а
  не правило из документации Apple: **похоже, одна болванка оставляет весь
  плейлист локальным**.
- За болванками стояли настоящие каталожные треки. В целевом каталоге по
  артисту, названию и длительности нашлись все 18 из первого плейлиста и 23
  из 33 из второго. Не нашлись десять треков рождественского джаза (Gregory
  Porter, Samara Joy, Oscar Peterson и другие).
- Чинить надо не копию на Маке, а создать плейлист через API с каталожными
  ID: облако само разошлёт его на оба устройства, после этого старую копию на
  Маке удалить. Удалять старую безопасно только когда новая уже приехала на
  Мак отдельным плейлистом с другим persistent ID, иначе можно снести сам
  облачный плейлист.
- **Каталожные ID из снимка медиатеки протухают.** Два ID из 98, взятые из
  `matched.json` (снимок от 10 сентября, использован 26-го), в каталоге уже
  не находились. API ответил 202 и молча их выкинул. Сами треки в медиатеке
  оставались и добавились в плейлист по библиотечному ID
  (`type: library-songs`, `i.…`), в конец списка.
- Два кураторских плейлиста Apple (`canEdit: false`), которые были в облачной
  медиатеке, из неё пропали, хотя на Маке остались. Причина неизвестна.
  Повторное добавление по `pl.…` вернуло их с **теми же** библиотечными ID
  (`p.…`), что были раньше.

## 10. Ограничения по частоте

Заявленный потолок Apple — около 20 запросов в секунду на пользователя, причём
эндпоинты медиатеки строже каталожных. Инструмент работает на ~3 запросах в
секунду и не поймал **ни одной ошибки 429** примерно за 12 000 запросов.

Обрывы сети (таймауты SSL-рукопожатия) случились дважды за длинную сессию —
повторять запрос стоит и на `URLError`/`TimeoutError`, а не только на
HTTP-ошибках.
